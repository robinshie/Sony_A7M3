## 原厂锐度请求

精确目标是 ILCE-7M3 4.04，内部版本 `37114_13.2026020901`。`viewUnified2.so` 原始 SHA-256 为 `f561a1e5fa0d10d55727dd4a10ced97c9613b698a40b489ff9317634485e5129`，`libbackup.so` 为 `b6420f8f7cacade524e1ba7c5b0d8b06691c22ed793dca084fdf1c1d9ae092f3`。

原始创意风格 setter 位于 view 库偏移 `0x420d18`，会修改整个配方和保存槽。新适配器 `payloads/a7-fl-sharpness-native.c` 只构造一个参数：

- 原厂 `Param<int>`：ID 392，值 −3…+3。
- 原厂请求目标 `@M00B`，动作 38。
- 分配和对象所有权转交遵循原始 setter；不调用 Backup 写接口。
- 返回 1 **只代表调用已发出**。原厂请求的返回寄存器不是已证实的成功标志，不能据此显示「完成」。

`research/sharpness_probe.py` 默认离线构建；只有 `--live` 才访问 USB。真机实验先校验机型、版本、完整已安装加载器及 r3 模块，保存完整设置快照，再逐次绑定代码字节及当前属性。请求后由另一条读取路径检查实际活动值，最后恢复原值。

本轮真机原状态为中性、第三风格槽、对比度 +1、饱和度 −1、锐度 −1。共检查 9 个字节属性：活动风格与三个活动参数、选中槽、三个槽内参数、槽内风格。

| 实验 | 活动锐度 `0x0107018a` | 槽内锐度 `0x01070a1d` | 其他 7 项 |
|---|---|---|---|
| 原始完整 setter：−3 / +3 | 253 / 3 | 253 / 3 | 保持原值 |
| 单参数请求：−3 / +3 | 253 / 3 | 255 / 255 | 保持原值 |
| 每轮结束恢复 | 255，即 −1 | 255，即 −1 | 全部与原状态一致 |

完整 setter 记录在私有 `.lab/sharpness-probe/1794392492648318000/`；单参数记录在 `.lab/sharpness-probe/1794392832978275000/`。这些只证明参数路径和恢复，不证明成片效果。实验后适配器改为忽略不明返回值；这个修改已重新完成离线 ARM 测试，未重新做真机往返，不能把旧负载日志当成新二进制的硬件认证。

进一步静态追踪发现 libObj 将锐度消息打包为 AV-CAM 控制 `0x403c`，接收者复制到内部锐度字段。另一个 `0x40f4` 控制调节 SharpnessGain。后者不是已确认的锐度范围或清晰度接口。AV-CAM 文件偏移与运行地址属于另一地址空间，不可直接当作 Linux 进程指针写入。

## 独立空间算法

`payloads/a7-fl-spatial.c` 接收独立的 8 位亮度平面，输出另一平面；没有访问机身缓冲区，没有调用 Sony ISP。算法是本项目自制近似，不能称为 A7 IV 原厂 FL 算法。

- 锐度 −3…+3：原像素与小半径均值的差，按有符号强度加回；0 为不锐化。
- 锐度范围 1…5：分别对应半径 5…1，数值越大处理越细；锐度为 0 时这项不产生影响。
- 清晰度 0…9：半径 16 的局部对比度，使用中间调权重，单像素改变量限制在 ±24。
- 两项都为零时逐像素保持亮度；恒定区域保持不变，边界使用复制扩展。
- 使用滚动行和累计值，复杂度随像素数线性增长；没有堆分配或浮点。工作区为 `70 × 宽度` 字节，6000 像素宽需要 420,000 字节，另外仍需输入和输出图像内存。
- 拒绝参数越界、尺寸/跨度不合法、长度不足、工作区未对齐及不允许的缓冲区重叠。

独立测试使用慢速二维卷积作为参考，覆盖 5 种尺寸、7 种图案及全部 350 组参数，共 12,250 个案例。Mac 运行 ASan/UBSan；相同 C 源码编译成 ARM，在 QEMU 中运行并逐像素核对。该测试不能说明机身处理速度、颜色空间正确性或拍摄稳定性。

## 临时图像元数据探针

进一步找到 `dataflowInfraFramework.so` 的 `C_DataflowInfra_StdData_YC::GetEntry_ImageSizeInfo`（偏移 `0x22300`，Thumb），以及 `libObj.so` 导入槽 `0x126ce20`。原厂 `GetData_All` 复制对象偏移 20 开始的 60 字节，标量访问器包含有效图像尺寸、DMM 句柄、压缩、排列、位深枚举及条带宽度。**这些字段的存在不代表已经取得像素，也不代表处理时拥有图像缓冲区。**

`research/yc_trace.py` 构建临时 RAM 探针：仅在精确库身份和原导入槽匹配时，将该槽指向保留在匿名内存中的记录包装函数。包装函数调用原函数一次、保留返回值，只复制成功返回的元数据；不做图像写入、文件 I/O、分配或等待。v1 最多记录 128 项，仅收集有效尺寸至少 2800×1800 的候选；该过滤现已由下述 v2 的独立最大样本槽替代。

ARM 包装函数通过 2,080 组测试，覆盖原函数失败、禁用、锁已占用、容量达到/超过上限、小尺寸跳过、结果和元数据一致性及数组边界。安装器只修改进程中的一个已核对导入槽，不改系统文件。停止时恢复原槽，保留匿名分配直到进程退出，避免已进入包装函数的调用访问被释放内存。

`research/yc_metadata_fixture.py` 另行提取原厂 25 个标量访问器和 60 字节整块访问器，在 QEMU 中使用 256 种已知字节模式，完成 431,616 项检查，核对 Python 解析器的字段偏移、长度和输出边界。枚举的实际含义及真实帧内容仍未验证。

v1 探针曾成功加载，记录在私有 `.lab/yc-trace/1794394519470077000/`。用户保持开机拍摄并回放大尺寸 JPEG 后，已读取并解除探针：`status=2, armed=0, count=0, dropped=0`，见 `.lab/yc-trace/1794396814049091000/`。这只说明没有符合 v1 尺寸过滤条件的记录，不能区分接口未被调用、调用失败或尺寸条件不匹配。原导入槽已经恢复；没有写入新的功能固件。v1 源码位于提交 `63f3951`。

v2 已增加调用/失败计数，取消小图像过滤，保留前 127 份成功记录，并用独立槽保存最大有效尺寸的样本，避免早期预览占满后漏掉照片。记录器不等待竞争中的锁，因此计数不包含未取得锁的并发调用。另新增 JPEG 编码入口记录器：观察 `libObj.so` 导入槽 `0x126b17c`，目标为 `libmpr.so` 偏移 `0x85ecbc` 的 `MprIf::EncodeStill`；只复制原调用的 64 字节 RegionInfo，不解引用其中的物理像素地址。

### 调用期的有界样本

`research/still_buffer_snapshot.py` 验证了迟读地址的局限：先核对机型、库和 `/proc/self/maps`，每区最多读取 256 字节。`.lab/still-buffer-snapshot/1794400717231904000/` 中，除一个已被堆复用的区域外，其余地址均不再映射。即使地址仍可读，也不能证明它仍属于照片。此工具不应被用作后续算法的缓冲区所有权证据。

`research/memory_read_probe.py` 只用自有 16 字节数组和无效地址测试故障可控的读取。相机 Linux 3.0.27 上 `process_vm_readv` 返回 `ENOSYS`；`/proc/self/mem` 的 `pread64` 正确返回自有数组，无效地址返回 `EIO`，文件描述符已关闭。记录在 `.lab/memory-read-probe/1794400917578970000/`。该次内存快照为总计约 110 MiB、空闲约 1.2 MiB、缓存约 41 MiB；不能据此承诺整帧软件滤波的可用内存或速度。ARM 系统调用号可对照 [Linux ARM UAPI 定义](https://github.com/torvalds/linux/blob/v3.10/arch/arm/include/uapi/asm/unistd.h)。

v6 的 `--kind write_samples` 在一次原写入调用返回时，复制完整 StillInfo，再通过 `/proc/self/mem` 对 12 个主图区域各采最多 256 字节；立即关闭描述符。复制不会修改图像，不做堆分配，后续调用不重复采样。模式 0–3 仍无文件 I/O；模式 4 有上述有限读取。原返回值保留，地址溢出、空区域、短读、打开失败及停止竞争均有检查。

- ARM 包装函数：10,332 案例、26,580,732 项检查。
- 安装/恢复：写入接口 19 案例、111 项检查。
- 采样辅助函数：30 案例、93,300 项检查。
- 加载 `.lab/yc-trace/1794401362408043000/`；拍照后在 `.lab/yc-trace/1794401471339656000/` 读取并解除，`status=2, armed=0, count=1, observed_calls=1, failures=0`。

实际样本中，StillInfo `+0x98` 区域长 1,772,544 字节，以 JPEG DQT 标记开头，随后有 DHT；`+0xa8` 和 `+0xb8` 以 JPEG SOI 开头，后者还有 EXIF。`+0x88` 为 `MWDI` 开头的未知格式；其他区域包括机型、版本、镜头、PrintIM 和标签表。现有 256 字节样本不足以确认 JPEG 图像尺寸。这证明该写入端拿到的是压缩数据及元数据，不能直接使用亮度滤波器。

## 实时方向：YAP 硬件细节模块

用户要求取景时也生效后，继续追踪 AV-CAM 的 YAP 代码。日志名及调用关系将 `job_YC_CalcParam (SYNC)` 与 `job_YC_SetParam (CAP)` 分开，包含增益、低通、掩膜、coring、亮度相关参数。**这是静态调用关系；目前没有执行完整的真实帧调度，也没有证明这些项目对应 A7 IV 的清晰度。** Sony 的 [A7 IV 帮助](https://helpguide.sony.net/ilc/2110/v1/en/contents/TP1000640837.html) 把锐度范围定义为作用于轮廓粗细的调节，并建议用拍摄后放大回放检查三项效果；不能仅根据菜单名称认定原厂内部算法相同。

以下仍为固定 AV-CAM 文件偏移，不能作为 Linux 地址使用：

| 位置 | 证据 |
|---|---|
| `0x3f872c` | 完整 `CalcLpf`：API 索引 3/4/6 取小表 `+0x27,+0x26,+0xb3,+0xb2`；1/2/5 取大表和选择字节；其他索引不写结果 |
| `0x401190`–`0x4011ca` | 同步计算依次调用低通、掩膜、coring、亮度相关参数、增益及 ACM 计算；静态追踪 |
| `0x3fb2e0`–`0x3fb350` | 静态照片流程取小表 `+0x26/+0x27`，组装两个 u16，经 `0x70fc20` 写低通参数；日志分别标识 `vaplpf/haplpf` |
| `0x70fc20`、`0x70fa24` | 原厂写入函数将两个 u16 打包到寄存器基址 `+0x15c1c`，设置对象脏标记 |
| `0x1141ec8` 的索引 133/134 | 小表目的偏移 `0x10557e6`、大表 `0x1058606` |
| `0x1141964`、`0x1141c18` | 小表两组均为属性 `0x30032`；大表按注册组为 `0x30033` 或 `0x30139`，尚不能混用 |
| `0x367f58`、`0x77a8c4` | 注册表将对应备份属性与目的缓冲区交给回调；通用回调按传入长度复制到注册目的区，静态追踪 |

`research/yap_lpf_native.py` 执行原厂完整低通选择器和写入函数，所有表、设备对象和寄存器均为有边界检查的 QEMU RAM。合成输入遍历 API、索引及数据模式，另遍历 65,536 组 u16 打包；使用私有备份时还执行两组真实表输入。**这些遍历不是硬件合法值枚举，不能据此扩大真机参数范围。**

本次候选夹具通过 330,752 案例、49,098,511 项检查，见私有 `.lab/yap-lpf-probe-01/qemu/`。`research/yap_lpf_probe_test.py` 的 14 个离线案例覆盖未知前像拒绝、部分写入、回读失败、恢复成功/失败、恢复日志和写入前备份。

`.lab/yap-readonly/1794403755291547000/` 真机回读三表均与之前备份一致：小表 2560 字节，两份大表各 5120 字节。直接通过维护文件接口读取 `/proc` 返回空内容，不能把这个结果当作内存布局证据。

随后执行了一次**仍待恢复的两字节诊断**：小表 `0x30032` 的 `+0x26,+0x27` 从原始 `1,1` 改为 `0,0`，其余 2558 字节及两份大表保持原值。只比较这两个选择状态，不声称已经有五档锐度范围。写入前保存完整 BK4，直接回读与整份 BK4 核对通过，记录为 `.lab/yap-lpf-probe-01/apply-1794404037621587000/`。没有替换 r3 固件，也没有发送保存命令；原厂其他保存行为仍可能持久化备份 RAM，所以用户验证后必须执行恢复，重启不等同于已恢复。

当前等待用户保持开机，观察取景、拍一张有细节的 JPEG 并接回。此实验尚未证明像素效果，也未开放剩余三项菜单。

```sh
# 离线原厂参数夹具
python3 research/yap_lpf_native.py --avcam "$A7M3_AVCAM"
python3 research/yap_lpf_probe_test.py
# 已准备私有恢复包后的状态与恢复；不要再次 apply 代替恢复
python3 research/yap_lpf_probe.py status --bundle .lab/yap-lpf-probe-01 --live
python3 research/yap_lpf_probe.py restore --bundle .lab/yap-lpf-probe-01 --live
```
