## 复现

```sh
python3 research/lut3d_native.py \
  --avcam "$A7M3_FIRMWARE_ROOT/0700_part_image/dev/nflasha3_unpacked/av-cam.bin"
```

预期 `QEMU_NATIVE_3DLUT_PASSED`，证明文件在 `.lab/lut3d-native/proof.json`，记录源码、固件片段、输入、ELF 和日志散列。固件及机身数据不进入 Git。

### JPEG 拍摄选表

使用同一机身的 BK4 `0x30001` 控制表，执行原厂描述符生成 `0x526a90` 和选表 `0x523894`。普通取景夹具选表 0；静态拍摄夹具按颜色空间分别选表 2（sRGB）和表 1（Adobe RGB）。原厂静态 Develop 构建器设置输入标志 `params[1]=1`，该分支不依赖预览缓存，重新打包当前选中的源表。早先的表 0 缓存复现仍适用于原来的夹具，但不能解释成需要修改静态 Develop 分支。

此前两张对照 JPEG 的互操作标识都是 `R03`（Adobe RGB）。因此此前只写表 0 的设置验证版不能覆盖这次拍摄，只改 sRGB 表也不足。r4 双拍摄表版更新表 0、1、2，其中表 1/2 为固定配方。当前 r5 在此基础上增强默认配方并接入五项色彩滑杆，冷启动后参数与拍摄色表回读一致，用户确认对比度 −9／+9 的照片差异明显；其他单项和两个颜色空间仍需分别补测。实现与边界见[机内菜单模块](native-creative-look.md#r5增强默认效果与拍摄端调节)。

在原来的测试命令上，使用实验前的原厂 BK4，并追加 `--capture-look`，可离线生成 `offline-capture-table1.bin` 和 `offline-capture-table2.bin`。两张表分别基于各自原厂表生成，保留属性尾部及原厂控制表。对每张表的 1–8 档强度，QEMU 核对原厂 → FL → 恢复的全部 405 节点，限制打包后的亮度和色差变化，避免跨越有符号编码边界时产生跳变。标记为 `NATIVE_3DLUT_CAPTURE_LOOK_PASSED`；低强度的测试验证的是数值边界，未标定实际色彩。

候选文件已接入[双拍摄表驻留模块](native-creative-look.md)，2026-11-12 模块已写入真机并完整回读；冷启动后的驻留状态和两张 FL 源表只读核对通过，用户确认开关可见差异。尚未读取新版开关对照 JPEG、分别验收两个颜色空间或量化恢复结果。QEMU 没有运行 Sony ISP，也没有验证真机缓存同步。不要把离线表文件当成更新包。

### 原厂备份源表

| 属性 | 运行缓冲区偏移 | 消费者 |
| --- | --- | --- |
| `0x00030004` | `0x10c0235` | 三平面表 0，前 1215 字节 |
| `0x00030005` | `0x10c0769` | 三平面表 1，前 1215 字节 |
| `0x00030006` | `0x10c0e09` | 三平面表 2，前 1215 字节 |
| `0x00030007` | `0x10c1571` | 三组两平面表，每组 162 字节 |

本机原厂备份中四项均为 1280 字节、属性位为 8；前三项非空、第四项全零。前三项 1215 字节后的尾部均为零；不据此把尾部视为可用存储。第三项有 64–127 的值，前两项有 128–255 的值，有符号缩放和七位截取不能混同。后续诊断和 FL 试用仅改变表 0，有单独原厂备份及恢复工具，见上述试用文档。

选择器用 `group=(selector>>5)&3`、`number=selector&15`。group 0、number 0–2 选择三平面；group 1、number 0–2 选择两平面；其余为空表。位 4 还参与 SD 条件。本测试固定 SD 关闭，未复现真实模式切换。发现这些属性不代表可以覆盖它们，仍需独立 FL 表及恢复原厂状态的设计。

## 存储格式

三平面逻辑形状为 5×9×9，`i=a*81+b*9+c`，三个分量位于 i、i+405、i+810。两平面形状为 9×9，第一分量置零，另外两分量来自 b*9+c、b*9+c+81，沿 a 重复五次。

每节点小端 u32：`((component0&127)<<16)|((component1&127)<<8)|(component2&127)`。Create 在 level 1–7 时先将源字节视为有符号八位数、乘 level、算术右移 3；关闭其他转换时，level 0/8/255 不缩放。不能将 level 0 直接理解为关闭效果。

[lut3d_format.py](../research/lut3d_format.py) 提供存储打包及解包，采用原厂其他分支钳位所用的 [-64,63] 代码范围，拒绝超界；它不是 RGB 到相机色彩编码的转换器。

bank 为 `(a&1)*4+(b&1)*2+(c&1)`，bank 内坐标递增：

| bank | 节点 | 输入字节偏移 | 寄存器内目的偏移 |
| --- | ---: | ---: | ---: |
| 0 | 75 | 0x000 | 0x17000 |
| 1 | 60 | 0x12c | 0x17200 |
| 2 | 60 | 0x21c | 0x17300 |
| 3 | 48 | 0x30c | 0x17400 |
| 4 | 50 | 0x3cc | 0x17500 |
| 5 | 40 | 0x494 | 0x17600 |
| 6 | 40 | 0x534 | 0x17700 |
| 7 | 32 | 0x5d4 | 0x17800 |

## 剩余接入工作

SD 转换引用坐标 [0,64,128,192,256]、[-128,-96,-64,-32,0,32,64,96,128] 和非线性扩展/压缩表。这支持亮度/色差修正的研究方向，尚不能确定通道、单位、传递函数及硬件插值。不能把 sRGB .cube 缩为 405 点就烧录。

仍需闭合原生菜单参数、模式选择、自定义表的独立存储与恢复、颜色编码和 JPEG 实拍。锐化/清晰度另需机内空间处理路径。现有 QEMU 八项调节和真机固件仍是不同实现。
