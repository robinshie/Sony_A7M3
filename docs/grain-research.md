# 颗粒优先研究（2026-11-14）

相机持久固件仍是已验收 r14。已完成合成缓冲区颗粒基准、内核模块加载与回调自检；普通拍摄已真实命中分块编码包装，完整输入记录确认当前模式没有暴露 CPU 源像素地址，正在追踪其上游 VFX 交接。没有刷入颗粒固件或修改真实照片像素。光晕后续研究。

## 最新范围：只处理拍摄成片

用户随后明确选择「拍完渲染，不要实时」。颗粒路线改为拍摄后处理，不再要求普通取景生效。目标优先是在 JPEG 编码前处理已完成拍摄的 YUV，保留色度，避免解码再编码造成额外损失；接口未确认前不承诺已经能在机内成片中生效。

新增 a7_film_capture_grain_dispatch：预览请求直接跳过，甚至不获取帧；仅拍摄路径从当前 FL／FL2／FL3 设置快照中读取颗粒，光晕强制关闭。颗粒为 0 或创意外观关闭时跳过处理。使用独占帧接口的 CPU 同步、处理、设备同步和释放顺序；工作区半径固定为 1，6000 像素宽时要求 42,000 字节工作区，未包含图像缓冲。

原始图像仍由调用者提供。该入口不接收压缩 JPEG，不负责读写 RAW／JPEG 文件，也没有安装到 Sony 拍摄调度器。源缓冲合法并不等于 JPEG 可以发布：修改后同步失败须隔离该帧，不能继续编码部分处理的内容。

Mac ASan/UBSan 与 ARM QEMU 的扩展测试均通过 7,311 案例、89,639,624 检查，包含三个风格各自的拍摄颗粒、连续预览请求零访问、提交时参数快照、光晕排除以及关闭／零强度跳过。证据 .lab/film-frame/proof.json。此前两路实时预览目标已被本节取代，颗粒不再以满足取景帧预算为前提。

## 本轮实现与验证

在 a7-film-frame.c 增加纯颗粒路径，只写亮度 Y，保留 Cb/Cr 与行尾填充。宽度大于参考宽度 576 时，缓存两条参考噪声扫描线，相邻输出行复用；保持原算法的整数舍入、尺度、种子、强度 0–9 和两种亮度范围。

缓存使用已有工作区中的 2,308 字节，无新增堆分配；公共接口仍要求原工作区大小，不宣称减少了接口内存要求。关闭颗粒时逐字节恒等。

主机 ASan/UBSan 对照原算法通过 1,680 组：四种 YUV 排列、两种范围、0–9 强度、三种种子、2/24/576/578/960/6000/16384 宽度。检查完整像素、色度、行尾填充及工作区边界。原帧内核及调度在主机和 ARM QEMU 均通过 7,307 案例、89,638,820 检查。

证据：.lab/grain-fast/proof.json、.lab/film-frame/proof.json。

## 接口研究结论

已有真实 UYVY 抽样来自解码／显示元数据路径，尚无普通连续取景独占写入证明。JPEG 编码阶段已有静态和 QEMU 控制流证据，但源句柄派生不等于 CPU 获得可写帧。原厂粗颗粒黑白属于照片效果分支，尚未证明可以独立叠加到彩色 FL。详见 [FL3 帧接口调查](fl3-film-controls.md)。

下一步仅定位拍摄完成到 JPEG 编码前的帧交接，确认格式、有效尺寸与跨度、写入所有权、缓存同步和释放时序。随后评估单张处理时间、连拍排队和取消；无需继续追踪普通取景入口。颗粒菜单尚未接进驻留模块；schema 4 的三个风格虽已预留颗粒字段，字段存在不等于画面生效。

## 真机缓存函数表与 DMM 独占机制（后续实查）

本轮进一步确认了真实装载环境。AV-CAM 使用 LIRO 的内核侧接口；它不是 `a7fl.so` 用户进程中可直接调用的函数。相机仍是 r14，以下操作只运行临时读取模块并清理，没有修改拍摄帧、加载新的内核模块或更新固件。

`research/cache_symbols_probe.py` 两次在真机读取 `/proc/kallsyms`。第二次还通过只读 `/dev/mem` 做了 9 次有界读取：

- 内核 `phys_mem_access_prot` 的代码片段与本地固定散列的 `vmlinux.bin` 一致。
- AV-CAM 地址转换包装函数的代码片段与本地 `av-cam.bin` 一致。
- AV-CAM 根地址为 `0x635c6000`，实际导入表为 `0x635c60b4`。
- 导入表 `+0x2fc`、`+0x300` 分别匹配当前内核符号中的 LIRO `cache_flush_range`、`cache_inv_range`；`+0x304`、`+0x308`、`+0x30c` 分别匹配 `arch_phys_to_noncache`、`arch_phys_to_cache`、`arch_va_to_phys`。

原厂 `liro.ko` 的代码与重定位表显示，两个缓存函数接收的是**物理地址和长度**：先转换为缓存地址，再调用 CPU 缓存接口；随后在存在相应外层缓存回调时，对物理起止地址执行清理或失效。函数名中的 `flush` 不能被理解成任意用户地址上的 `msync`。本轮只确认了真机函数表对应关系，**没有调用缓存函数，也没有证明某张照片已经同步成功**。

只读证据：`.lab/cache-symbols/1794667780803609000/`，`route_status=0`、两段代码匹配，临时文件清理完成。前一次仅符号读取在 `.lab/cache-symbols/1794667399847343000/`。实际 LIRO 装载地址可能变化，不能把本次符号地址直接硬编码到发布版。

同时检查了原厂 `dmm.ko`：`SetUnitAccInfo` 是访问日志记录，不是锁。`dmm_unit_ctrl_Open` 的模式 4 才有独占状态转换。新增 `research/dmm_exclusive_fixture.py`，在 QEMU 执行原厂 Open、Close 和句柄解析代码，仅替换模块加载重定位和资源记录所在内存。**24 项检查通过**，证据 `.lab/dmm-exclusive/proof.json`：

- 无现存打开引用、无 rendezvous 引用时，模式 4 进入状态 3。
- 独占期间，模式 0、1、4 均被拒绝；关闭后恢复可打开状态。
- 普通共享引用尚未全部关闭时拒绝独占；最后一个引用关闭后可独占。
- 错误句柄代次、失效资源、未知模式和计数溢出不会取得独占。

这证明的是 DMM 的资源状态机，不证明拍摄 DMA 的所有消费者都遵守这个锁。现有生产 `a7_dmm_open` 仍使用原来的共享读取模式，没有擅自改成模式 4。

下一项实际接入工作已经明确：在 AV-CAM 的 JPEG 前阶段建立内核侧回调，取得该次拍摄的资源、格式和跨度，在对应资源生命周期内调用颗粒与上述缓存接口，再交回原厂编码流程。现有 `a7fl.so` 只能提供菜单和设置；单独往它加入这几个内核地址不能完成调用。内核回调尚未实现和真机验证，所以本轮仍无可刷入的拍后颗粒候选。

本机已有 Sony 提供的内核源码包 `sony-linux-kernel.tar.gz`；可用于后续核对模块 ABI。官方来源为 [ILCE-7RM3／ILCE-7M3 源码发布页](https://oss.sony.net/Products/Linux/DI/ILCE-7RM3.html)。这不包含完整的专有 AV-CAM 实现，也不能代替当前运行版本的 ABI 核对。

复现 DMM 状态机：

```sh

```

## 内核模块与 JPEG 前回调（2026-11-14）

已从本机 Sony GPL 源码准备模块构建环境。当前现代 GCC 构建增加了 GNU89 兼容参数和编译器属性兼容头；它们只解决构建问题。是否可加载，另用原厂模块和真机检查确认：

- 原厂 `liro.ko` 与自制模块的 `vermagic` 都为 `3.0.27_nl-rt106+ SMP preempt mod_unload ARMv7 `。
- `struct module` 均为 316 字节，初始化／退出入口重定位位于 `0xbc`／`0x134`。
- `research/kernel_probe.py` 的只读模块在真机加载、读取、正常卸载均返回 0。证据：`.lab/kernel-probe-runs/1794668802876910000/`。

随后实现 `research/kernel_probe/capture_probe.c` 与 `capture_bridge.S`。插入点为原厂 JPEG 阶段的标记调用 `0x6390619c`（AV-CAM 文件偏移 `0x34019c`），此时原厂已经获得上下文，尚未构造和提交 JPEG 编码请求。

不能直接覆盖该阶段入口的前 8 字节：原厂入口是 4 字节入栈、2 字节栈调整，随后为 4 字节调用，8 字节覆盖会截断调用。当前临时探针只替换对齐的完整 4 字节标记调用，以专用 `UDF.W` 通过 Linux 原有异常回调跳转到 Thumb 桥接代码。桥接保留调用参数、栈和状态标志，记录后执行原厂标记函数并返回下一条原厂指令。

Linux 使用 ARM 模式，未启用 Thumb 内核模块重定位。桥接中的 ARM／Thumb 交互采用寄存器间接调用和绝对地址重定位，构建器拒绝此内核不支持的 Thumb 分支重定位。

`research/jpeg_stage_fixture.py --kernel-callback` 在 QEMU 运行原厂阶段代码，触发实际 CPU 未定义指令异常并走同一桥接：29 次 JPEG 回调、48 个场景、2,056 项检查通过。夹具替换了异常派发器和底层图像服务，不是完整 Sony 内核、传感器或 JPEG 编码器。未插入回调的原阶段回归仍为 48 个场景、1,878 项检查通过。

真机先运行同一候选模块的私有指令自检，确认原厂异常派发器能正确进入回调并返回，再正常卸载；之后才启用拍摄入口探针。证据包 `.lab/capture-kernel/1794669527502351000/` 同时保存三种操作的加载器散列、源码身份和原始结果。`arm` 成功时报告等待拍摄，**不等于拍摄回调已经命中**。

临时探针只复制上下文中的 160 字节元数据，不获取 DMM 写锁、不触碰图像像素、不调用图像缓存同步、不修改持久固件。首次命中后只计数，不重复采样。`collect` 先恢复原厂调用并同步指令缓存，再读取记录。启用后的模块与异常回调固定保留至相机重启，避免延迟返回跳到已释放代码；因此不会强制卸载，也不会作为固件发布。

### 首次实际拍摄结果：未命中该阶段

用户完成一次 JPEG（L）拍摄与回放后，最终回读 `.lab/capture-kernel/1794669527502351000/collect-1794670566085464000.bin`：入口命中为 **0**，恢复原厂调用标志为 **1**。因此该次普通拍摄没有经过这个插入点，不能把静态控制流或私有回调自检当成真实编码接通。没有在该轮处理像素或刷固件。

回读时修复了两项工具问题：

- UTM 维护模式切换后曾保留旧 USB 节点；只保留最新重新枚举的设备，并按已观察到的路径、VID/PID 和设备号核对后移除旧 guest 节点。仅断开 UTM CLI 的新节点反而会留下旧连接并返回管道错误，不能把“唯一设备”本身当成通信正常。
